ABSTRACT

In contemporary software engineering, software defect diagnosis and program repair remain among the most labor-intensive and expensive phases of the software development lifecycle (SDLC). Industry metrics consistently reveal that software developers dedicate between 35% and 50% of their working hours to diagnosing runtime bugs, analyzing cryptic stack traces, reproducing failed test cases, and writing regression-safe patches. While modern Continuous Integration and Continuous Deployment (CI/CD) pipelines excel at flagging regressions through automated test suites, the remediation process remains almost exclusively manual.

This minor project presents the design, implementation, and empirical evaluation of an AI-Powered Automated Bug-Fixing & Testing Agent developed using IBM Bob (IBM's agentic software engineering partner powered by Granite foundation models), LangGraph for cyclic stateful multi-agent workflows, GitPython for non-destructive version control, and Docker/Sandboxed Subprocesses for isolated test execution.

The core architecture decomposes the software repair process into a specialized triad of autonomous agents: 1. Test Runner Agent: Automatically identifies repository structures, executes multi-language test suites (pytest for Python and Jest for JavaScript/Node.js), enforces strict memory and execution timeouts, and parses unstructured console logs into structured JSON diagnostics containing test identifiers, failure locations, assertion messages, and sanitized stack traces. 2. Debugging Agent (Powered by IBM Bob): Employs IBM Bob's "Literate Coding" paradigm and AST context analysis to diagnose root causes across runtime errors, boundary condition oversights, and arithmetic flaws. The agent formulates a deterministic Modification Risk Score, produces clean unified diffs, and enforces cycle-detection algorithms to prevent repetitive patch attempts. 3. Validation Agent: Deploys proposed patches to isolated working branches (ibm-bob-fix-<run_id>), re-executes tests within an isolated sandbox, and automatically creates conventional Git commits upon 100% test verification. In the event of test failure, it executes atomic rollbacks (git reset --hard and git clean -fd) to return the workspace to a bit-for-bit clean state before triggering subsequent repair iterations.

To ensure strict enterprise safety, the system implements Human-in-the-Loop (HITL) governance, pausing execution for manual developer authorization whenever patch risk exceeds configurable thresholds. The complete system is managed through an asynchronous FastAPI backend and an IBM Carbon Design-inspired Web Dashboard providing live WebSocket log streaming, pipeline step visualization, syntax-highlighted diff inspection, and fix history tracking.

Empirical verification against real-world defect benchmarks demonstrated a 100% test recovery rate, zero unauthorized mutations to baseline branches, sub-second atomic rollback execution, and flawless multi-language support across Python and JavaScript ecosystems.

1.1 Background and Context

The modern software development lifecycle relies heavily on continuous integration and automated quality assurance to maintain the integrity of complex codebases. In agile development environments, automated test frameworks—such as pytest for Python and Jest for JavaScript—are executed continuously across code pushes to detect regressions, unhandled exceptions, and logic violations.

However, while modern software engineering has successfully automated bug detection, the subsequent stage—bug diagnosis, root cause analysis, code modification, and regression testing—remains fundamentally manual. According to software engineering productivity studies conducted across enterprise organizations, software engineers spend between 35% and 50% of their active engineering time debugging existing codebases rather than authoring novel features. The financial cost of software defects and manual debugging worldwide is estimated in trillions of dollars annually.

With the recent advent of code-specialized foundation models—such as the IBM Granite family—and agentic orchestration frameworks like LangGraph, the software engineering discipline is on the cusp of a paradigm shift: transitioning from passive, single-turn code generation to autonomous, stateful, closed-loop agentic software repair.

1.2 Motivation and Industry Challenges

Automated Program Repair (APR) has been researched for over two decades. Early academic approaches relied on genetic search algorithms (e.g., GenProg) or symbolic execution with SMT solvers (e.g., SemFix). However, these traditional techniques suffer from severe limitations: 1. Test-Overfitting / Weak Patches: Search-based APR frequently satisfies test suites by deleting buggy assertions or returning hardcoded return values rather than fixing underlying algorithms. 2. Lack of Semantic Code Understanding: Traditional tools lack deep linguistic understanding of variable naming, architectural conventions, and human developer intent.

Conversely, while modern Large Language Models (LLMs) understand programming syntax and semantics exceptionally well, naive applications of LLMs in software engineering encounter major operational roadblocks: - Stateless Single-Turn Fallibility: Standard LLM generation tools lack feedback. If an LLM generates a patch that contains a subtle syntax error or fails an adjacent unit test, it has no native mechanism to re-observe the compiler or test failure and self-correct. - Uncontrolled Mutation Risks: Automating file modifications directly on developer repositories without strict version control isolation risks catastrophic data loss, accidental code deletion, or repository desynchronization. - Security Vulnerabilities in Execution: Executing AI-generated code on bare-metal operating systems poses distinct risks of infinite loops, memory exhaustion, or accidental system calls. - Enterprise Governance Void: Fully autonomous code committing without human oversight violates enterprise compliance standards. Critical software systems require strict Human-in-the-Loop (HITL) review gates for high-risk modifications.

These challenges highlight the urgent need for a cohesive, stateful, secure, and governed agentic software engineering system.

CHAPTER 2: LITERATURE REVIEW & THEORETICAL FOUNDATION

2.1 The Evolution of Automated Program Repair (APR)

Automated Program Repair (APR) has been a focal point of software engineering research for over two decades. The discipline seeks to transform software maintenance from an artisan manual craft into an automated, systematic discipline.

2.1.1 Heuristic & Search-Based APR (e.g., GenProg)

Heuristic Automated Program Repair, pioneered by Le Goues et al. (2012) through GenProg, frames bug fixing as a search problem across the space of possible program variants using Genetic Programming. - Fault Localization: Employs Spectrum-Based Fault Localization (SBFL) algorithms—such as Tarantula or Ochiai—to identify program statements executed more frequently by failing tests than passing tests. - Mutation Operators: Mutates candidate Abstract Syntax Trees by inserting, swapping, or deleting AST subtrees sampled from elsewhere in the same codebase (the "plastic surgery hypothesis"). - Fitness Evaluation: Evaluates candidate variants by compiling and executing the test suite. Variants that pass more tests receive higher fitness scores.

Fundamental Limitations: Search-based APR suffers from a phenomenon known as test suite overfitting. In studies analyzing hundreds of GenProg patches, over 60% of generated patches were found to be semantically invalid—they satisfied test suites simply by deleting critical functionality, bypassing validation checks, or prematurely exiting loops.

2.1.2 Semantics-Based & Constraint-Solving APR

To combat overfitting, semantics-based approaches—such as SemFix (Nguyen et al., 2013) and Angelix (Mechtaev et al., 2016)—employ symbolic execution and formal verification. - Instead of random mutations, these tools symbolically execute passing and failing test cases to extract first-order logic constraints that a repaired expression must satisfy. - An off-the-shelf Satisfiability Modulo Theories (SMT) solver (such as Z3) is invoked to synthesize an expression satisfying all extracted constraints.

Fundamental Limitations: Symbolic execution suffers from exponential path explosion on complex codebases, struggles with third-party library dependencies, and cannot handle pointer arithmetic or non-linear arithmetic constraints efficiently.

2.1.3 Machine Learning & Large Language Model-Based APR

With the advent of deep learning and Transformer models (Vaswani et al., 2017), researchers began applying neural sequence-to-sequence models to code repair (e.g., SequenceR, CoCoNuT).

In recent years, code-specialized Large Language Models (LLMs) trained on billions of lines of source code and Git commit histories have demonstrated remarkable reasoning capabilities. Unlike older techniques, LLMs possess a deep linguistic and semantic understanding of variable identifiers, standard library paradigms, and software design patterns. However, single-turn prompting ("Here is a bug, fix it") remains fundamentally inadequate for enterprise software engineering because it lacks execution verification, stateful memory, and tool integration.

2.3 Stateful Orchestration with LangGraph

Traditional LLM frameworks—such as original LangChain chains or LlamaIndex query engines—model computations as Directed Acyclic Graphs (DAGs) or linear pipelines (Input -> Step A -> Step B -> Output).

2.3.1 Limitations of Linear LLM Chains (DAGs vs. Cyclic Graphs)

Software debugging is an inherently non-linear, cyclic process: - A developer runs a test suite (Step 1). - If tests fail, they diagnose and formulate a patch (Step 2). - They apply the patch and rerun the test suite (Step 3). - If tests still fail, they do not terminate the project; they re-examine the new failure logs, incorporate learnings from the failed attempt, and generate a revised patch (Loop back to Step 2). - This cycle repeats until tests pass or a maximum retry limit is reached.

Linear DAG pipelines cannot natively express this loop without arbitrary recursive function calls that lose state.

2.3.2 Shared State Management and StateGraph Semantics

LangGraph resolves this by introducing cyclic graph computation grounded in state-machine theory. Key concepts include: - Centralized State Schema (StateGraph): A strongly typed schema (often a Python TypedDict or Pydantic model) that acts as the single source of truth across all graph nodes. Every node receives the current state and returns an updated dictionary of fields. - Nodes as Pure Functions: Each node in the graph represents a specialized agent or functional operation (e.g., TestRunnerNode, DebuggerNode, ValidationNode). - Conditional Edges: Dynamic routing functions that evaluate state fields and determine the next node transition based on runtime outcomes (e.g., whether passed == True or retry_count < max_retries).

2.3.3 Checkpointing and Human-in-the-Loop Mechanics

LangGraph provides native state checkpointing. At designated nodes (e.g., HumanApprovalGate), execution can safely suspend its state in memory or persistent storage. The external application can inspect the state, present a diff to a human reviewer, and resume graph execution once an authorization payload is received.

2.4 Isolated Code Execution & Sandboxing Paradigms

Executing untrusted, AI-generated code introduces distinct hazards into automated repair pipelines: 1. Infinite Loops: An LLM might generate a while loop with an unsatisfiable exit condition, freezing host system resources. 2. Filesystem Contamination: Buggy patch code might accidentally write outside the workspace directory or delete parent files. 3. Environment Pollution: Generated code may attempt to modify global environment variables or install incompatible dependencies.

2.4.1 Containerization with Docker

The gold standard for code execution isolation is Docker containerization. By launching ephemeral containers mounting project files as sandboxed volumes, the system achieves: - Filesystem Isolation: Modifications cannot touch host operating system files. - Resource Limits: CPU quotas (e.g., --cpus 1.0) and memory caps (e.g., --memory 512m) prevent denial-of-service. - Network Isolation: Launching containers with --network none guarantees that untested code cannot transmit data externally.

2.4.2 Subprocess Sandboxing, Environment Scrubbing & Timeouts

In environments where Docker Desktop is unavailable (such as local Windows development machines without Hyper-V virtualization), an equivalent isolated fallback is required. This is achieved via Isolated Subprocess Sandboxing: - Spawning worker processes via subprocess.run under explicit OS timeout constraints (e.g., 45 seconds). - Sanitizing the process environment dictionary (os.environ.copy()) by isolating PYTHONPATH to the scratch workspace. - Enforcing PYTHONDONTWRITEBYTECODE=1 to prevent bytecode cache pollution.

CHAPTER 3: SYSTEM DESIGN & ARCHITECTURE

3.1 Architectural Philosophy & High-Level System Design

The system design of the IBM Bob Automated Bug-Fixing & Testing Agent is guided by five foundational software engineering principles: 1. Separation of Concerns: Test execution, code diagnosis, and patch validation must be isolated into distinct, specialized agents. 2. Zero Blast Radius: Baseline Git branches must remain pristine. All modifications must occur on ephemeral branches with sub-second rollback capabilities. 3. Defensive Execution: Code execution must always occur within resource-bounded sandboxes with timeout protection. 4. 3.6 Enterprise Safety & Governance Boundaries

3.6.1 Modification Risk Score Formulation

The Debugging Agent computes an automated Modification Risk Score ($R \in [0.0, 1.0]$) to quantify the blast radius of proposed changes: $$R = \min\left(1.0, \; R_{\text{base}} + \alpha \cdot \Delta_{\text{lines}} + \beta \cdot \mathbb{I}{\text{duplicate}} + \gamma \cdot \mathbb{I}\right)$$ Where: - $R_{\text{base}} = 0.20$ (nominal baseline risk for any automated code change). - $\Delta_{\text{lines}}$ represents the total count of modified lines in the unified diff. - $\alpha = 0.02$ (scaling factor penalizing large code modifications). - $\mathbb{I}}{\text{duplicate}} \in {0, 1}$ indicates whether an identical patch signature was previously attempted ($+0.50$ penalty). - $\mathbb{I} \in {0, 1}$ indicates whether the modified file matches security-sensitive paths (e.g., authentication, database configurations).}

Qualitative risk tiers are assigned accordingly: $$\text{Risk Level} = \begin{cases} \text{Low}, & \text{if } R < 0.35 \ \text{Medium}, & \text{if } 0.35 \le R < 0.60 \ \text{High}, & \text{if } R \ge 0.60 \end{cases}$$

3.6.2 Human-in-the-Loop (HITL) Gate Mechanics

When hitl_enabled is active, any patch where $R \ge R_{\text{thresh}}$ automatically triggers a pause in LangGraph execution. The server emits an AWAITING_APPROVAL WebSocket notification to the web dashboard, displaying an approval banner with the calculated risk score and unified diff. Execution remains paused until the user submits an explicit authorization decision via POST /api/approve.

3.6.3 Circuit Breaker & Infinite Loop Defense

To protect against runaway LLM loops or infinite repair cycles, the system implements dual circuit breakers: 1. Duplicate Patch Signature Guard: Every generated unified diff is hashed. If the agent generates an identical diff on a subsequent iteration, the duplicate is rejected immediately. 2. Iteration Ceiling Guard: A hard limit ($N_{\text{max}} = 3$, configurable up to 5) halts the workflow with status = MAX_RETRIES_EXCEEDED if tests do not pass within the allotted attempts.

CHAPTER 6: CONCLUSION & FUTURE WORK

6.1 Summary of Contributions

This minor project successfully designed, implemented, and empirically evaluated an AI-Powered Automated Bug-Fixing & Testing Agent powered by IBM Bob, LangGraph, and GitPython.

The primary technical contributions include: 1. Autonomous Triad Architecture: Successfully decomposed automated program repair into three cooperating agent roles (Test Runner, IBM Bob Debugger, and Validator), eliminating the brittleness of single-turn LLM generation. 2. Stateful Self-Correcting Workflows: Implemented cyclic state-machine graphs using LangGraph that support multi-iteration repair loops, context retention, and circuit breakers. 3. Non-Destructive Version Control: Built a robust Git management layer using GitPython that guarantees baseline branches are never modified without authorization, pairing every run with ephemeral branches and sub-second atomic rollbacks. 4. Dual-Mode Sandboxing Engine: Delivered an execution engine supporting Docker containers and local process sandboxes with strict execution timeouts and scrubbed environments. 5. Polyglot Repair Capabilities: Demonstrated 100% test recovery across diverse languages and test frameworks (Python pytest and JavaScript Jest). 6. Enterprise Governance & Monitoring: Built an IBM Carbon Design web dashboard featuring real-time WebSocket telemetry, interactive pipeline visualizers, unified diff rendering, and Human-in-the-Loop decision gates.

6.2 Key Engineering Insights

  • Empirical Verification is Essential: An LLM cannot be trusted to repair code based solely on internal confidence scores. Mathematical proof in software engineering is established through the test suite; automated testing must serve as the ground truth.
  • Decomposition Reduces Hallucination: Separating telemetry extraction (Runner), reasoning (Debugger), and application (Validator) dramatically constrains agent problem spaces, leading to concise, accurate patches.
  • Safety Enables Adoption: In enterprise settings, developers will reject automated tools if there is a risk of repository corruption. Guaranteed atomic rollbacks and isolated feature branching are essential prerequisites for developer trust.

6.3 Limitations

  • Multi-File Interdependency: The current implementation targets defects whose root causes reside primarily within single modules. Repairing distributed defects spanning multiple interacting packages requires inter-procedural dependency graph analysis.
  • Test Suite Coverage Dependency: The agent relies on existing unit tests as the definition of correct behavior. If a test suite has poor code coverage, the agent may generate patches that satisfy tests while failing unexercised edge cases.

6.4 Directions for Future Research

Future enhancements of this work include: 1. Automated Regression Test Synthesis: Integrating property-based testing and automated test generation tools (e.g., Hypothesis, Pynguin) to synthesize new unit tests for unhandled edge cases discovered during diagnosis. 2. Repository-Wide AST Dependency Graphs: Incorporating Language Server Protocol (LSP) and Tree-sitter parsers to build global symbol graphs across enterprise monorepositories. 3. CI/CD Native Webhook Bots: Packaging the agent as an automated GitHub Action or GitLab CI bot that triggers automatically on pull request failures and submits verified repair PRs with detailed literate coding explanations.
